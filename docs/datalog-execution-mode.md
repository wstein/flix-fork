# Compile-Time Sequential Execution Mode for Flix Fixpoint3

This document describes the design, configuration, and verification of the compile-time selectable sequential execution mode for the Flix compiler and its bundled `Fixpoint3` Datalog/RAM solver library.

---

## 1. Overview and Motivation

Flix's `Fixpoint3` solver executes a lowered relational-algebra program (RAM). By default, its execution strategy utilizes concurrency:
- Statement parallelism via virtual thread spawning (`RamStmt.Par`).
- Search parallelism via parallel B+ tree traversals (`BPlusTree.parForEach`).
- Region-level synchronization and per-thread search context cloning (`copyCtx`).

Sequential mode exists for single-threaded, embedded, and deterministic environments, where creating virtual threads is either unavailable or undesirable. It is **not** a performance optimization: see the measurements in section 6.

A naive runtime boolean flag inside the interpreter is insufficient because both parallel and sequential code branches remain statically reachable, preventing tree shaking and dead-code elimination. This was verified empirically -- see section 4.

This feature implements a **compile-time selectable sequential mode** that guarantees:
1. **Semantic Parity**: Equivalent minimal-model stratified Datalog and lattice fixpoint computation results.
2. **Parallel Path Erasure**: The parallel interpreter family (`evalStmtParallel`, `evalOpParallel`, `evalSearchOrQueryOpParallel`, `evalSearchOrQueryOpLatticeParallel`, `parEvalSearchOrQueryOp`, `parEvalSearchOrQueryOpLattice`, and `copyCtx`) is pruned by Flix's inliner and tree-shaker passes, and no `Region.spawn` call site remains anywhere in `Fixpoint3.Interpreter`. This concerns the interpreter's own parallelism; see *Scope* below for what it does not cover.
3. **Zero Context Cloning**: Sequential evaluation shares and mutates execution environments without copying.

### Scope

The option governs the RAM **interpreter** only. It is not a way to obtain a program free of concurrency primitives, and it should not be relied on as one -- for example when targeting a runtime that forbids threads or locks.

Comparing the generated bytecode of the two builds for the same program, the complete difference is two call sites:

| Call site | Parallel | Sequential |
|---|---|---|
| `Fixpoint3.Interpreter.evalStmtParallel` → `Region.spawn` | present | **erased** |
| `Fixpoint3.Interpreter.evalOpParallel` → `Region.spawn` | present | **erased** |

Everything else is identical in both builds and is therefore *not* affected by this option:

| Remaining construct | Reached through |
|---|---|
| `Fixpoint3.Interpreter.interpret` → `Thread.startVirtualThread` | `Map` operations used to build and marshal indexes, which inline `RedBlackTree`'s `par (...) yield` |
| `RedBlackTree.parMapWithKey`, `RedBlackTree.parExists` → `Thread.startVirtualThread` | the `@ParallelWhenPure` operations on `Map` and `Set` |
| `BPlusTree.Lock`, `Fixpoint3.ReadWriteLock` → `java.util.concurrent.locks.StampedLock` | the B+ tree's concurrent index locking |
| `Concurrent.ReentrantLock`, `Concurrent.Condition`, `Concurrent.CyclicBarrier` | `Concurrent.Channel` |

Note in particular that `interpret` calls `Thread.startVirtualThread` in **both** builds. This is not a remnant of the erased evaluator: the interpreter's own parallelism spawns into the dynamic region `rc2` and therefore compiles to `Region.spawn`, never to `startVirtualThread` (see `GenExpression.scala`, `AtomicOp.Spawn`, where only a `Static` region takes the direct path). The call comes from `RedBlackTree` code inlined into `interpret`, which is why it is present regardless of the mode. `TestDatalogReachability` asserts this distinction explicitly rather than relying on the absence of the parallel def names, because the inliner can fold a def into its caller and thereby remove the symbol without removing the behavior.

Removing the remaining constructs would mean giving `Map`, `Set`, `BPlusTree`, and `Concurrent` the same compile-time treatment. That is a larger change than a Datalog execution option and is deliberately not attempted here.

## 2. Compiler Options and CLI

### CLI Flag
The compiler accepts the experimental flag:
```bash
flix compile --Xdatalog-execution=parallel|sequential <files>
```

- `parallel` (default): Compiles Fixpoint3 with full parallel statement and search capabilities.
- `sequential`: Rewrites the Fixpoint3 configuration constant to `false`, causing the optimizer to erase the parallel execution routines.

### Compiler API Options
In Scala:
```scala
import ca.uwaterloo.flix.util.{DatalogExecution, Options}

val options = Options.Default.copy(
  xdatalogExecution = DatalogExecution.Sequential // or DatalogExecution.Parallel
)
```

## 3. Architecture and Implementation

### Phase Pipeline Integration (`DatalogExecutionMode`)
1. **Flix Standard Library Stub**: `Fixpoint3.Options.enableParallelExecution(): Bool` returns `true` by default in Flix source.
2. **AST Rewrite Phase**: When `xdatalogExecution == DatalogExecution.Sequential`, the compiler phase `DatalogExecutionMode` intercepts `TypedAst.Root` and rewrites `Fixpoint3.Options.enableParallelExecution`'s body to `Constant.Bool(false)`. If the definition is missing while the full standard library is loaded, the phase fails with an `InternalCompilerException` rather than silently producing a parallel build.
3. **Dispatch & Inlining**: In `Fixpoint3.Interpreter.interpretWithDatabase`:
   ```flix
   if (Options.enableParallelExecution())
       evalStmtParallel(rc, ctx, parLevel(), stmt)
   else
       evalStmtSequential(rc, ctx, stmt)
   ```
4. **Optimization and Tree Shaking**:
   - `Optimizer` / `Inliner` inlines the constant condition `if (false)` and eliminates the dead branch.
   - `TreeShaker1` and `TreeShaker2` strip the whole parallel evaluator family, along with `copyCtx` and `BPlusTree.parForEach`.
5. **Incremental Compilation**: The rewrite is applied *after* the incremental caches are updated, so `cachedTyperAst` always holds the un-rewritten AST and the rewrite is recomputed from the current options on every run. Changing `xdatalogExecution` on an existing `Flix` instance therefore takes effect immediately and does **not** invalidate any cache.

## 4. Interpreter Split

The `Fixpoint3.Interpreter` module is structured into two independent evaluator families:

### Parallel Evaluator Family
- `evalStmtParallel(rc, ctx, parLevel, stmt)`: Handles `RamStmt.Par` by spawning virtual threads in a sub-region with `copyCtx`.
- `evalOpParallel(rc, ctx, parLevel, op)`: Dispatches to `BPlusTree.parForEach` when `parLevel > 0`.
- `parEvalSearchOrQueryOp` & `parEvalSearchOrQueryOpLattice`: Clones `ctx` for worker threads.

### Sequential Evaluator Family
- `evalStmtSequential(rc, ctx, stmt)`: Evaluates `RamStmt.Par` as a deterministic sequential loop (`Vector.forEach(evalStmtSequential(rc, ctx), stmts)`), without spawning regions or threads. Sharing one `ctx` across the branches is safe because each branch runs to completion before the next one starts, and `bindTuple` writes every environment slot before it is read.
- `evalOpSequential(rc, ctx, op)`: Uses standard sequential `BPlusTree.forEach`.
- `evalSearchOrQueryOpSequential` & `evalSearchOrQueryOpLatticeSequential`: Operates directly on the shared context with zero allocations for context cloning.

### Why two families rather than one gated evaluator

The duplication is deliberate. Collapsing both families into a single evaluator whose two divergence points are gated on `enableParallelExecution()`, i.e.

```flix
case RamStmt.Par(stmts) =>
    if (enableParallelExecution()) /* spawn */ else Vector.forEach(evalStmt(rc, ctx, parLevel), stmts)
...
case RelOp.Search(...) =>
    if (enableParallelExecution() and parLevel != 0) /* parForEach */ else /* forEach */
```

was implemented and measured. It removes ~150 lines, but it **breaks guarantee 2**: with a merged, self-recursive `evalOp`, the folded condition does not eliminate the parallel branch in every specialization, and the sequential build retains live `Region.spawn` call sites inside `Fixpoint3.Interpreter.evalOp` (observed with `TestDatalogReachability`). Tree shaking works at whole-def granularity, which is exactly what the split provides and what a single merged function cannot. The two families must therefore be kept in sync by hand; `TestDatalogExecutionParity` and `CompilerSequentialSuite` are the guard against drift.

## 5. Verification & Test Coverage

1. **Option Plumbing & AST Rewrite** (`TestDatalogExecutionMode.scala`):
   - CLI option parsing (`--Xdatalog-execution=parallel|sequential`, invalid value rejection).
   - Constant AST replacement verification under both modes, and the no-op case without the standard library.
   - Mode switching on an existing compiler instance with warm incremental caches, in both directions.

2. **Semantic Parity** (`TestDatalogExecutionParity.scala` & `CompilerSequentialSuite.scala`):
   - Recursive transitive closures and multi-stage derivations.
   - Multiple index merge groups (`RamStmt.Par`).
   - Lattice relations and least-upper-bound computations.
   - Stratified negation.
   - Provenance (`psolve`/`pquery`, exercising `RelOp.ProvProject`).
   - Functional predicates (`RelOp.Functional`), `inject ... into`, `solve ... project`, and join-with-existing-model solving.
   - The full `main/test/flix/` suite re-executed under sequential mode.

3. **Bytecode Reachability & Erasure** (`TestDatalogReachability.scala`):
   - The parallel evaluator family is absent from a sequential build and the sequential family is present, and vice versa.
   - No `Region.spawn` call site remains in `Fixpoint3.Interpreter` in a sequential build, and the offending def is reported by name when one does.
   - The interpreter's spawn call sites are compared between the two builds directly, so that a parallel body inlined into its caller cannot pass by virtue of having lost its symbol.
   - A **positive control** asserts that every construct claimed to be erased is genuinely present in a parallel build. Without it, an assertion with nothing to find is indistinguishable from a successful erasure -- an earlier version of this test asserted the absence of symbols (`Thread.startVirtualThread`, `CyclicBarrier`, `RedBlackTree.parMapWithKey`) that were never present in either build, and used a pure `main` whose Datalog computation was optimized away entirely, so all of its assertions held vacuously.

## 6. Performance

Sequential mode is a compatibility and determinism feature, not a speed-up. Measured with a warmed-up JIT, 9 runs per configuration, timing only the solve (compilation excluded), on transitive-closure workloads:

| Workload | Parallel (median) | Sequential (median) |
|---|---|---|
| Sparse: 900 nodes, 1 out-edge each | 70 ms (57-130) | 67 ms (58-95) |
| Dense: 260 nodes, 2 out-edges each | 314 ms (293-327) | 391 ms (376-395) |

On workloads with little available parallelism the two modes are equivalent, and sequential mode has a visibly tighter spread because it does not create threads. On workloads with real parallelism, sequential mode costs roughly 20-25% throughput. Choose it when determinism, single-threaded execution, or the absence of virtual threads matters -- not to make Datalog faster.
