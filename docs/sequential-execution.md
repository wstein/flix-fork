# Compile-Time Sequential Execution Modes

Flix's standard library uses concurrency in two places that a program cannot opt out of at runtime: the `Fixpoint3` Datalog solver evaluates its relational-algebra program in parallel, and the pure operations on `Map`, `Set`, and `DelayMap` evaluate in parallel once the collection is large enough.

This document describes two experimental compiler options that compile that parallelism away, how they are implemented and verified, and what they cost.

---

## 1. Motivation

Sequential mode exists for single-threaded, embedded, and deterministic environments, and for targets that forbid threads or locks outright, such as a WebAssembly runtime. It is **not** a performance optimization: see the measurements in section 8.

A runtime flag would not be enough. Both branches of a runtime `if` remain statically reachable, so the tree shaker must keep the parallel code and everything it depends on. The options therefore work at compile time: each is backed by a library function returning a constant, which the compiler rewrites, after which the optimizer folds the guarded branch and the tree shaker removes what only that branch kept alive.

---

## 2. The options

| Option | Governs | Library switch |
|---|---|---|
| `--Xdatalog-execution=parallel\|sequential` | the `Fixpoint3` RAM interpreter | `Fixpoint3.Options.enableParallelExecution` |
| `--Xcollection-execution=parallel\|sequential` | pure operations on `Map`, `Set`, `DelayMap`, and `RedBlackTree` | `Concurrent.Options.enableParallelEvaluation` |

Both default to `parallel`. They are independent: the second changes how every collection operation in the program is evaluated, not only the solver's, so it is deliberately not implied by the first.

In Scala:

```scala
import ca.uwaterloo.flix.util.{ExecutionMode, Options}

val options = Options.Default.copy(
  xdatalogExecution = ExecutionMode.Sequential,
  xcollectionExecution = ExecutionMode.Sequential
)
```

---

## 3. What each option removes

Measured on a small Datalog program, comparing the generated bytecode across all four combinations:

| `--Xdatalog-execution` | `--Xcollection-execution` | Classes | `Region.spawn` | `Thread.startVirtualThread` | `Concurrent` classes | `StampedLock` calls |
|---|---|---|---|---|---|---|
| parallel | parallel | 2617 | 3 | 6 | 38 | 10 |
| sequential | parallel | 2585 | **0** | 6 | 38 | 10 |
| parallel | sequential | 2405 | 3 | **0** | **0** | 10 |
| sequential | sequential | 2373 | **0** | **0** | **0** | 10 |

The two options are orthogonal, and each removes exactly what it claims:

- **`--Xdatalog-execution=sequential`** removes the interpreter's three `Region.spawn` sites — two in `evalOpParallel` (search parallelism, from `BPlusTree.parForEach` folded into it) and one in `evalStmtParallel` (statement parallelism, from `RamStmt.Par`).
- **`--Xcollection-execution=sequential`** removes all six `Thread.startVirtualThread` sites and all 38 classes of the `Concurrent` locking layer.

That the locking layer disappears with the *collection* option is not a coincidence, and is worth stating explicitly: `par (...) yield` does not spawn threads directly. `Lowering.mkParChannels` allocates one channel per fragment, spawns each fragment at the `Static` region, and waits on the channels. `Concurrent.Channel` in turn uses `ReentrantLock`, `Condition`, and `CyclicBarrier`. The locking layer is therefore a *consequence* of `RedBlackTree`'s use of `par`, not an independent dependency, and it goes away with it.

### What remains

The ten `StampedLock` calls are untouched by either option. They come from the B+ tree's concurrent index locking, in `BPlusTree.Lock` (eight) and `Fixpoint3.ReadWriteLock` (two). Neither option is a guarantee that the compiled program is free of concurrency primitives, and neither should be relied on as one. Removing the locks would mean making `BPlusTree` single-threaded, which changes its concurrency contract rather than merely its evaluation strategy, and is not attempted here.

Note also that `Fixpoint3.Interpreter.interpret` calls `Thread.startVirtualThread` whenever `--Xcollection-execution=parallel`, in both Datalog modes. This is not a remnant of the erased evaluator: the interpreter's own parallelism spawns into a dynamic region and therefore compiles to `Region.spawn`, never to `startVirtualThread` (see `GenExpression.scala`, `AtomicOp.Spawn`, where only a `Static` region takes the direct path). The call comes from `RedBlackTree` code inlined into `interpret` through the `Map` operations that build and marshal the solver's indexes, which is why only the collection option removes it.

## 4. Implementation

### The `LibraryOptions` phase

1. **Library switch.** Each option is backed by a zero-argument library function returning `true`.
2. **Rewrite.** `LibraryOptions` sets the body of each switch whose option is `sequential` to `Constant.Bool(false)`. If a switch is missing while the full standard library is loaded, the phase fails with an `InternalCompilerException` rather than silently producing a parallel build.
3. **Fold and shake.** The `Inliner` folds each `if` on the now-constant switch, and `TreeShaker1` and `TreeShaker2` remove the definitions that only the dead branch reached.
4. **Ordering.** The phase runs after `Redundancy`, since replacing a body can leave a formal parameter unused, and after the incremental caches are written, so that `cachedTyperAst` always holds the un-rewritten AST. The rewrite is therefore recomputed from the current options on every run: changing either option on an existing `Flix` instance takes effect immediately and does **not** invalidate any cache.

A detail worth knowing when writing such a switch: the `Inliner` folds `and`, but does not fold `not`. Write `if (enableX() and cond)`, never `if (not enableX() or ...)`.

### Datalog: two evaluator families

`Fixpoint3.Interpreter` holds two complete evaluator families, selected by the switch:

- **Parallel** — `evalStmtParallel` handles `RamStmt.Par` by spawning virtual threads in a sub-region with `copyCtx`; `evalOpParallel` dispatches to `BPlusTree.parForEach` when `parLevel > 0`; `parEvalSearchOrQueryOp` and `parEvalSearchOrQueryOpLattice` clone the context for worker threads.
- **Sequential** — `evalStmtSequential` evaluates `RamStmt.Par` as a deterministic loop over the statements. Sharing one context across the branches is safe because each branch runs to completion before the next one starts, and `bindTuple` writes every environment slot before it is read. `evalOpSequential` uses `BPlusTree.forEach`, and the search helpers operate directly on the shared context with no cloning.

The duplication is deliberate. Collapsing both families into a single evaluator whose two divergence points are gated on the switch was implemented and measured: it removes ~150 lines, but the folded condition does not eliminate the parallel branch in every specialization of the self-recursive `evalOp`, and the sequential build retains live `Region.spawn` call sites. Tree shaking works at whole-def granularity, which is what the split provides and what a single merged function cannot. The two families must therefore be kept in sync by hand; `TestDatalogExecutionParity` and `CompilerSequentialSuite` are the guard against drift.

### Collections: one gate per structure

`Map`, `Set`, `DelayMap`, and `RedBlackTree` each decide whether to evaluate a pure operation in parallel with a private `useParallelEvaluation`, which tests the size of the underlying tree. Each now tests the switch first, so that a sequential build folds the size test away along with the parallel branch it guards. Operations given an impure function already took the sequential path and are unaffected.

## 5. Verification

1. **Option plumbing** (`TestLibraryOptions.scala`): CLI parsing for both options including invalid values, the rewritten body of both switches under all four combinations, the no-op without the standard library, and mode switching on an existing compiler instance with warm caches.

2. **Datalog parity** (`TestDatalogExecutionParity.scala`, `CompilerSequentialSuite.scala`): recursive transitive closures, multi-stage derivations, merge groups, lattices, stratified negation, provenance via `psolve`/`pquery`, functional predicates, `inject ... into`, `solve ... project`, and join-with-existing-model solving — plus the full `main/test/flix/` suite re-executed under sequential mode.

3. **Collection parity** (`TestCollectionExecutionParity.scala`): `Map.count`, `Map.sumWith`, `Map.exists`, `Map.map`, and `Set.count`/`Set.exists` over collections large enough that parallel mode genuinely takes the parallel path, plus a case with an impure function.

4. **Erasure** (`TestDatalogReachability.scala`, `TestCollectionReachability.scala`): each asserts that the constructs it claims are erased are absent from a sequential build — and, in a **positive control**, that they are present in a parallel one. The control is not optional: an assertion that never had anything to find is indistinguishable from a successful erasure, and an earlier version of the Datalog test asserted the absence of symbols that were never present in either build, over a program whose fixpoint computation had been eliminated as dead code, so every one of its assertions held vacuously.

   The Datalog test additionally compares the interpreter's spawn call sites between the two builds directly, because the absence of a symbol is weaker than the absence of its body: the inliner can fold a def into its caller, removing the symbol while the behavior lives on.

## 6. Performance

Both options cost throughput. Measured with a warmed-up JIT, nine runs per configuration, timing only the work and not compilation:

| Workload | Parallel (median) | Sequential (median) |
|---|---|---|
| Datalog, sparse: 900 nodes, 1 out-edge each | 70 ms | 67 ms |
| Datalog, dense: 260 nodes, 2 out-edges each | 314 ms | 391 ms |
| Collections: two `Map.count` passes over 200,000 entries | 129 ms | 140 ms |

On workloads with little available parallelism the two modes are equivalent, and sequential mode has a visibly tighter spread because it creates no threads. On workloads with real parallelism, sequential Datalog costs roughly 20-25% and sequential collections roughly 10%. Choose either when determinism, single-threaded execution, or the absence of threads matters — not to make a program faster.
