# Compile-Time Sequential Execution Modes

Flix's standard library uses concurrency in two places that a program cannot opt out of at runtime: the `Fixpoint3` Datalog solver evaluates its relational-algebra program in parallel, and the pure operations on `Map`, `Set`, and `DelayMap` evaluate in parallel once the collection is large enough.

It also locks its concurrent index structures, whether or not any thread exists to contend for them.

Underneath both sits a third place, which is not the library at all: the runtime the backend emits for every program. A region tracks and joins child threads, a lazy value locks while it is forced, and fresh identities come from an atomic counter — in a program that has one thread and never mentions concurrency.

This document describes the experimental compiler option that compiles all of that away, how it is implemented and verified, and what it costs.

---

## 1. Motivation

Sequential mode exists for single-threaded, embedded, and deterministic environments, and for targets that forbid threads or locks outright, such as a WebAssembly runtime. It is **not** a performance optimization: see the measurements in section 6.

A runtime flag would not be enough. Both branches of a runtime `if` remain statically reachable, so the tree shaker must keep the parallel code and everything it depends on. The options therefore work at compile time: each is backed by a library function returning a constant, which the compiler rewrites, after which the optimizer folds the guarded branch and the tree shaker removes what only that branch kept alive.

---

## 2. The options

There is one option, `--Xsequential`, and it sets three library switches together:

| Library switch | Governs |
|---|---|
| `Fixpoint3.Options.enableParallelExecution` | the `Fixpoint3` RAM interpreter |
| `Concurrent.Options.enableParallelEvaluation` | pure operations on `Map`, `Set`, `DelayMap`, and `RedBlackTree` |
| `Concurrent.Options.enableLocking` | the locking in `BPlusTree` and `Fixpoint3`, and the counter in a `BPlusTree` |

It also changes what the backend emits, which no library switch can reach:

| Emitted for every program | Under the option |
|---|---|
| `Region` | no child threads: no queue, no join, no thread of its own, and no `spawn` |
| `Lazy` | forced without a lock |
| `Global` | fresh identities from a plain counter rather than an atomic |
| `par (...) yield` | one binding per fragment on the current thread rather than one channel and one thread |
| `spawn` | rejected where it stands |

The first two library switches are strategy choices: each selects between two implementations of the same contract, so either value of either one is sound. The third is not, and neither are the first three rows of the second table: dropping the locks, the region's bookkeeping, the lazy value's lock, and the atomic gives up thread safety, which is sound in exactly one situation -- when nothing left in the program can run in parallel. The last two rows are sound whatever the program does: evaluating the fragments of a `par (...) yield` in order is a schedule the parallel form already permits, and refusing to compile a `spawn` is a refusal rather than a change of meaning.

That asymmetry is why there is a single option rather than one per switch. An option per switch would make the unsound state expressible -- and, worse, expressible by accident: options are applied in the order they are given, so `--Xsequential --Xdatalog-execution=parallel` would leave the locks elided while restoring the parallel evaluator. Rejecting that after the fact would mean a validation rule, to be revisited every time another switch is added. Deriving all three from one option leaves nothing to validate.

The `Options` fields keep the switches separate, so that the compiler API can still set them individually and the tests can attribute each erased construct to the switch responsible for it. `xassumeSingleThreaded` is named after the precondition it asserts rather than the effect it has.

In Scala:

```scala
import ca.uwaterloo.flix.util.{ExecutionMode, Options}

// The equivalent of --Xsequential. Setting a subset is possible here, and is how the tests
// establish which switch removes what, but only this combination is sound.
val options = Options.Default.copy(
  xdatalogExecution = ExecutionMode.Sequential,
  xcollectionExecution = ExecutionMode.Sequential,
  xassumeSingleThreaded = true
)
```

## 3. What the options remove

Measured on a small Datalog program, comparing the generated bytecode across all four combinations:

| `enableParallelExecution` | `enableParallelEvaluation` | Classes | `Region.spawn` | `Thread.startVirtualThread` | `Concurrent` classes | `StampedLock` calls |
|---|---|---|---|---|---|---|
| on | on | 2662 | 3 | 7 | 42 | 10 |
| off | on | 2630 | **0** | 7 | 42 | 10 |
| on | off | 2421 | 3 | **0** | **0** | 10 |
| off | off | 2389 | **0** | **0** | **0** | 10 |

The two switches are orthogonal, and each removes exactly what it claims:

- **`enableParallelExecution = false`** removes the interpreter's three `Region.spawn` sites — two in `evalOpParallel` (search parallelism, from `BPlusTree.parForEach` folded into it) and one in `evalStmtParallel` (statement parallelism, from `RamStmt.Par`).
- **`enableParallelEvaluation = false`** removes all seven `Thread.startVirtualThread` sites and all 42 classes of the `Concurrent` locking layer.

That the locking layer disappears with the *collection* switch is not a coincidence, and is worth stating explicitly: `par (...) yield` does not spawn threads directly. `Lowering.mkParChannels` allocates one channel per fragment, spawns each fragment at the `Static` region, and waits on the channels. `Concurrent.Channel` in turn uses `ReentrantLock`, `Condition`, and `CyclicBarrier`. The locking layer is therefore a *consequence* of `RedBlackTree`'s use of `par`, not an independent dependency, and it goes away with it.

### `--Xsequential`

The ten `StampedLock` calls are untouched by either of the two switches above. They come from the B+ tree's concurrent index locking, in `BPlusTree.Lock` (eight) and `Fixpoint3.ReadWriteLock` (two). `--Xsequential` removes those as well, because it sets all three switches:

| Configuration | Classes | `Region.spawn` | `startVirtualThread` | `Concurrent` classes | `StampedLock` calls |
|---|---|---|---|---|---|
| default | 2662 | 3 | 7 | 42 | 10 |
| `--Xsequential` | 2314 | **0** | **0** | **0** | **0** |

Both lock wrappers gain a second, lockless case, and every operation on them tests `enableLocking` rather than matching on the wrapper, so that the branch holding the Java lock folds away. Without a lock, no writer can invalidate an optimistic stamp, so `valid` is always `true`, the stamp accessors return a non-zero constant, and the unlock and yield operations do nothing.

One operation does not get a lockless answer. `BPlusTree.Lock.isLocked` asks whether a thread holds the lock, and a build with no locks cannot answer it. Returning `false` would be worse than useless: the three callers of `isLocked` are invariant checks of the form `not isLocked(..)`, which would then pass without having checked anything. So `isLocked` aborts under elision, and those callers ask `enableLocking` first and skip the conjunct explicitly. A build without locks checks the structural invariants and openly does not check the lock ones.

### The generated runtime

None of the above touches what the backend emits for every program, and that carried concurrency of its own. Counting every call into `java.util.concurrent` or `java.lang.Thread`:

| Program | Default | `--Xsequential` |
|---|---|---|
| `println` of a list sum | 11 | **0** |
| a `lazy` value forced once | 14 | **0** |
| a two-fragment `par (...) yield` | 20 | **0** |
| two `BPlusTree.put`s and a `size` | 23 | **0** |
| the solver program above | 47 | **0** |

The eleven in the first row are the floor: a program that mentions no concurrency at all still gets a region that queues, joins, and starts threads, and a `Global` whose identity counter is an atomic. A lazy value adds a `ReentrantLock`, and a `par (...) yield` adds a channel per fragment, the thread that fills it, and the 22 `Concurrent` classes behind it.

Under the option all of it is gone, in every program: a region has no children and no `spawn`, a lazy value is forced without a lock, `Global` counts with a plain field, and a `par (...) yield` becomes one binding per fragment. The `par` case is also the largest single saving in the table -- 238 classes down to 164 -- because the channel machinery goes with it.

That last one deserves a word, since it is a change in how a *program's* own code is compiled rather than the library's. `par (a <- e1; b <- e2) yield e` says the fragments may be evaluated independently, not that they must be evaluated at once; evaluating them in order is one of the schedules it permits. The fragments are pure, which is what makes their order immaterial. A `spawn`, by contrast, has no sequential reading at all, and is rejected rather than reinterpreted.

This is the configuration to use for a target that has no threads, such as a WebAssembly runtime.

### What the elision is exposed to

`xassumeSingleThreaded` asserts that nothing in the program creates a thread. The compiler cannot
check that in general, but it does not have to take it on faith either: it compiles every `spawn`
into a rejection, so a program that breaks the assertion says so where it breaks it, rather than
somewhere downstream. The alternative -- running the child on the current thread -- is worse than it
looks. It satisfies the region's own guarantee, since work that has already run has certainly
finished by the time the region exits, but a child that waits for its parent, as both ends of a
channel rendezvous do, would wait forever. That is not hypothetical: it is what the corpus did
before the rejection was added, in `Test.Exp.Concurrency.Select`.

The seven corpus files that spawn are therefore excluded from `CompilerFullySequentialSuite`, and
listed there by name. `par (...) yield` is not among them: it is a way of writing an expression
rather than a way of writing a thread, so the option lowers it to a binding per fragment instead of
rejecting it.

One route out remains: a program can call `java.lang.Thread` itself through Java interop, which the
compiler has no say over. It is therefore worth being precise about what such a program could
actually race on.

The solver does not expose either elided lock to user threads.

Neither lock is reachable from outside a solve. The working indexes (`Indexes[r]`) and the `Boxing`
that owns the `ReadWriteLock`s are scoped to the region of a single `solve` and never escape it. The
only thing that ever shared them was the parallel evaluator, which this option erases. Solving an
existing model does not adopt its trees either: `Boxing.initializeFacts` reads them and builds fresh
region-local facts keyed by `Int64`.

The `BPlusTree`s that do escape -- the model built by `marshallDb` in the `Static` region -- are
complete before they become reachable, and every entry point of `Fixpoint3.Solver` treats them as
read-only thereafter:

| Entry point | Effect on an escaped tree |
|---|---|
| `runSolver`, `runSolverWithProvenance` | read during `Boxing.initializeFacts`; output built fresh by `marshallDb` |
| `union` (`<+>`) | read as the *source* of a merge into a fresh destination |
| `projectSym` | aliased into a new `Model` |
| `rename`, via `substitute` | aliased under a new key |
| `injectInto1..15` | not involved: builds region-local, then escapes |
| `facts0..15`, via `factsOfInternal` | read into a region-local buffer |
| `provenanceOf` | `memberOf` read; the `Provenance` path iterates the tree and writes only region-local scratch |

Note that `projectSym` and `rename` *alias* rather than copy, so one tree can belong to several
models. That makes the read-only property load-bearing: a future operation that wrote to a tree
reached from a `Model` would corrupt every model sharing it, elision or not.

Concurrent readers of a structure nobody writes need no lock, so a program that spawns threads and
uses Datalog does not race on anything this option elided.

`BPlusTree` and `RedBlackTree` are public modules, so a program can call their parallel operations
directly -- `BPlusTree.count`, `BPlusTree.parForEach`, `RedBlackTree.parCount`, and the rest --
without going through `Map`, `Set`, or the solver. For `BPlusTree` that would be a race introduced
by the option itself, since `--Xsequential` also removes that tree's locks. Each of those operations
is therefore gated at its own spawn site rather than at its callers. `TestPublicParallelApis` calls
each one on its own and checks that it spawns by default, does not under `--Xsequential`, and
returns the same answer either way.

Note also that `Fixpoint3.Interpreter.interpret` calls `Thread.startVirtualThread` whenever `enableParallelEvaluation` is on, whatever the Datalog switch is set to. This is not a remnant of the erased evaluator: the interpreter's own parallelism spawns into a dynamic region and therefore compiles to `Region.spawn`, never to `startVirtualThread` (see `GenExpression.scala`, `AtomicOp.Spawn`, where only a `Static` region takes the direct path). The call comes from `RedBlackTree` code inlined into `interpret` through the `Map` operations that build and marshal the solver's indexes, which is why only the collection switch removes it.

## 4. Implementation

### The `LibraryOptions` phase

1. **Library switch.** Each option is backed by a zero-argument library function returning `true`.
2. **Rewrite.** `LibraryOptions` sets the body of each switch that is turned off to `Constant.Bool(false)`. If a switch is missing while the full standard library is loaded, the phase fails with an `InternalCompilerException` rather than silently producing a parallel build.
3. **Fold and shake.** The `Inliner` folds each `if` on the now-constant switch, and `TreeShaker1` and `TreeShaker2` remove the definitions that only the dead branch reached.
4. **Ordering.** The phase runs after `Redundancy`, since replacing a body can leave a formal parameter unused, and after the incremental caches are written, so that `cachedTyperAst` always holds the un-rewritten AST. The rewrite is therefore recomputed from the current options on every run: changing the options on an existing `Flix` instance takes effect immediately and does **not** invalidate any cache.

A detail worth knowing when writing such a switch: the `Inliner` folds `and`, but does not fold `not`. Write `if (enableX() and cond)`, never `if (not enableX() or ...)`.

### Datalog: two evaluator families

`Fixpoint3.Interpreter` holds two complete evaluator families, selected by the switch:

- **Parallel** — `evalStmtParallel` handles `RamStmt.Par` by spawning virtual threads in a sub-region with `copyCtx`; `evalOpParallel` dispatches to `BPlusTree.parForEach` when `parLevel > 0`; `parEvalSearchOrQueryOp` and `parEvalSearchOrQueryOpLattice` clone the context for worker threads.
- **Sequential** — `evalStmtSequential` evaluates `RamStmt.Par` as a deterministic loop over the statements. Sharing one context across the branches is safe because each branch runs to completion before the next one starts, and `bindTuple` writes every environment slot before it is read. `evalOpSequential` uses `BPlusTree.forEach`, and the search helpers operate directly on the shared context with no cloning.

The duplication is deliberate. Collapsing both families into a single evaluator whose two divergence points are gated on the switch was implemented and measured: it removes ~150 lines, but the folded condition does not eliminate the parallel branch in every specialization of the self-recursive `evalOp`, and the sequential build retains live `Region.spawn` call sites. Tree shaking works at whole-def granularity, which is what the split provides and what a single merged function cannot. The two families must therefore be kept in sync by hand; `TestDatalogExecutionParity` and `CompilerSequentialSuite` are the guard against drift.

### Collections and locks: one gate per structure

`Map`, `Set`, `DelayMap`, and `RedBlackTree` each decide whether to evaluate a pure operation in parallel with a private `useParallelEvaluation`, which tests the size of the underlying tree. Each now tests the switch first, so that a sequential build folds the size test away along with the parallel branch it guards. Operations given an impure function already took the sequential path and are unaffected.

Gating the dispatch is not sufficient on its own, because the parallel operations are themselves public. Each one -- `RedBlackTree.parCount`, `parExists`, `parForAll`, `parSumWith`, `parMapWithKey`, `parLimitBy`, and `BPlusTree.parForEach` -- is therefore a thin wrapper that tests the switch and delegates either to its parallel body or to the sequential twin it already used as its own base case. Gating at the spawn site rather than at the call sites covers every caller, including ones that do not exist yet. `BPlusTree` is gated on the *solver's* switch rather than the collection one, since it is the solver's index structure; either switch being off is enough for safety, because the locks are only elided when both are.

---

### The generated runtime: two variants of a class

The runtime classes cannot be gated by a library switch, because they are not written in Flix. `BackendObjType` emits a second variant of each one when `Options.isSingleThreaded` holds:

- **`Region`** keeps only its exit handlers. The queue of children, the region's own thread, the field carrying a child's exception, and the `spawn` method are all about child threads, and there are none. The two methods that moved an exception between threads remain, because a region exit still calls one of them, and do nothing.
- **`Lazy`** drops the `ReentrantLock` and the `tryCatch` that existed only to release it. The lock kept two threads from forcing at once; with one thread the expression is read, run, and cleared without interruption. A thunk that throws now propagates directly.
- **`Global`** replaces the `AtomicLong` behind `newId` with a plain `long`. The atomic made the read and the increment one step, which they already are on one thread.

Two things outside `BackendObjType` follow from the same predicate. `GenExpression` compiles `AtomicOp.Spawn` into a rejection rather than a thread, at both region kinds -- this is the one place the compiler decides how a spawn happens, which is why the region no longer needs a `spawn` method to refuse it. And `Lowering.mkParYield` binds the fragments in order instead of building a channel and a thread for each.

`Options.isSingleThreaded` is not `xassumeSingleThreaded`: it also requires both execution modes to be sequential. The CLI cannot express anything else, but the compiler API can, and this is what keeps it from producing an unsynchronized program under a configuration that would still run the library's own threads.

## 5. Verification

1. **Option plumbing** (`TestLibraryOptions.scala`): CLI parsing for both options including invalid values, the rewritten body of both switches under all four combinations, the no-op without the standard library, and mode switching on an existing compiler instance with warm caches.

2. **Datalog parity** (`TestDatalogExecutionParity.scala`, `CompilerSequentialSuite.scala`): recursive transitive closures, multi-stage derivations, merge groups, lattices, stratified negation, provenance via `psolve`/`pquery`, functional predicates, `inject ... into`, `solve ... project`, and join-with-existing-model solving — plus the full `main/test/flix/` suite re-executed under sequential mode.

3. **Collection parity** (`TestCollectionExecutionParity.scala`): `Map.count`, `Map.sumWith`, `Map.exists`, `Map.map`, and `Set.count`/`Set.exists` over collections large enough that parallel mode genuinely takes the parallel path, plus a case with an impure function.

4. **Execution** (`CompilerFullySequentialSuite.scala`): the corpus, 307 of its 314 files, executed as `--Xsequential` compiles it. Lock elision is a compile-time change whose effect is only observable at run time -- unlocked code either produces the same answers or it does not, and a residual wait would hang rather than fail -- so compiling it is not evidence. For the same reason, every parity program above is executed in this configuration too. The seven files left out are the ones that spawn, which the option asserts the program does not; they are named in the suite and run in every other one.

5. **The generated runtime** (`TestSequentialRuntime.scala`): a region holds its allocations and nests, a lazy value forces to the same value repeatedly and through another lazy value, a `par (...) yield` yields the same value including when nested, and a `BPlusTree` counts its entries -- each run under both the default options and `--Xsequential`, since the runtime replacements are reached by every program rather than through the library. A `spawn` is separately asserted to fail under the option and to succeed without it.

6. **Erasure** (`TestDatalogReachability.scala`, `TestCollectionReachability.scala`, `TestSequentialReachability.scala`): each asserts that the constructs it claims are erased are absent from a sequential build — and, in a **positive control**, that they are present in a parallel one. The control is not optional: an assertion that never had anything to find is indistinguishable from a successful erasure, and an earlier version of the Datalog test asserted the absence of symbols that were never present in either build, over a program whose fixpoint computation had been eliminated as dead code, so every one of its assertions held vacuously.

   The Datalog test additionally compares the interpreter's spawn call sites between the two builds directly, because the absence of a symbol is weaker than the absence of its body: the inliner can fold a def into its caller, removing the symbol while the behavior lives on. `TestSequentialReachability` asserts that the locks *survive* when the two mode options are set without the umbrella, which keeps the claim about which option removes them honest.

   `TestSequentialReachability` deliberately does **not** assert that a `--Xsequential` build has no spawn site. Under that option the backend compiles every `spawn` into a rejection, so no build has one, and the assertion would hold whatever the library did. What it asserts instead is that no *rejection* was emitted either, which is where a `spawn` the library still reached would show up.

## 6. Performance

Measured with [`bench/sequential-execution.flix`](bench/sequential-execution.flix), on an Apple M2 Pro with 12 cores under JDK 21. Each run does three warm-up iterations and nine timed ones and reports the median; only the work is timed, not compilation. The table gives the *lowest* median over seven runs per configuration, because the machine was not quiet: individual runs came in as much as three times higher, in both configurations, and the lowest observation is the one least contaminated by whatever else was running.

| Workload | Default | `--Xsequential` |
|---|---|---|
| Datalog: 400-node chain, 79,800 derived paths | 536 ms | 207 ms |
| Datalog: 260 nodes, 2 out-edges each, 67,600 paths | 356 ms | 196 ms |
| Datalog: 700-node cycle, 490,000 paths | 2766 ms | 1625 ms |
| Collections: two `Map.count` passes over 200,000 entries | 120 ms | 127 ms |
| 1,000,000 forces of already-forced `lazy` values | 5 ms | 3 ms |
| 1,000,000 region entries, each allocating an array | 12 ms | 5 ms |
| `BPlusTree`: 200,000 puts and a `size` | 30 ms | 24 ms |

Three things are worth reading carefully here.

**Sequential Datalog did not cost throughput at any size measured.** An earlier revision of this document recorded it as 20-25% *slower* on a workload of the same shape. That no longer reproduces: at every size tried, including one deriving nearly half a million tuples, the sequential solver finished sooner, and with a far tighter spread. This is not a claim that the parallel evaluator is pointless — it is a claim that the size at which it repays its thread, channel, and lock overhead is larger than anything measured here. Measure your own workload before concluding either way.

**Sequential collections still cost a little**, about 6% on this one, which is the only row where the option is slower. Two `Map.count` passes over 200,000 entries is exactly the shape the parallel evaluation was written for.

**The runtime replacements are neutral to slightly positive, and for a reason worth knowing.** Removing a lock, an atomic, and a queue halved two microbenchmarks, but the absolute numbers — 5 ns per region entry, 5 ns per force — say that the JIT had already made the originals nearly free: an uncontended lock is biased, and a queue that never escapes is scalar-replaced. Do not choose this option for speed on the JVM. Choose it when the code must not merely be fast but must not *exist*, which is what a target without threads requires.
